HTML-in-Canvas overview[c]
The HTML-in-Canvas API bridges the gap between the interactive and accessible world of the DOM and the high-performance, pixel-level control of `<canvas>`.


Video overview of the HTML-in-Canvas API


For years, web developers had to face trade-offs when building visually demanding web applications:


Technology
	Strengths
	Limitations
	`<canvas>`
	* Low-level pixel control: Direct access to the GPU to drive advanced 2D and 3D graphics pipelines, custom shaders, and offscreen workers.
* High-performance rendering: Efficiently renders heavy, data-dense UIs.
	

* No Web platform features: Common operations like text selection, copy/paste, right-click actions, and responsive text layout must be manually implemented in JavaScript, adding substantial bundle weight.
* No browser features: The pixel grid is opaque to the browser. Features like accessibility, Find-in-Page, auto-translate, or autofill aren't supported in canvas natively and require fallback implementation.
	`HTML` 
	* Semantic, rich UI out of the box: Built-in form controls, responsive typography, or multi-line wrapping powered by the browser.
* Deep browser integration: Support for accessibility (screen readers), Find-in-Page, and standard interactions (text highlighting, copy/paste), live translation, autofill.
* Support for debugging and testing, for example, with DevTools.
	* Limited ability to control performance for complex layouts: As DOM complexity grows, the default performance characteristics hit limits.
* UX effects are limited to standard HTML, CSS, and SVG. Pixel manipulation, particle effects, and shaders are not available.
	

HTML-in-Canvas eliminates this compromise. The API allows developers to draw live DOM subtrees directly into 2D, WebGL, or WebGPU canvas contexts—while the browser natively retains user interactivity, accessibility trees, and browser-level integrations.
Before HTML-in-Canvas
Before this API, developers building canvas-heavy UIs had to choose between two approaches, each with their own downsides:
1. Rendering text directly as canvas pixels (`fillText()`). Apps drew text and UI controls imperatively as raw pixels. This resulted in the following downsides:
* Accessibility breakdown: Screen readers and assistive tools cannot read canvas pixels unless developers manually construct and sync an invisible fallback DOM.
* Loss of browser features: Users cannot search with Find-in-Page (Ctrl/Cmd+F), copy/paste text naturally, trigger context menus, or use browser translation and spellcheck.
* Complex typography engines: Supporting internationalization requires bundling massive JavaScript layout engines.
2. Floating HTML overlays on top of canvas. For example, using libraries that position standard HTML elements over the canvas by calculating bounding boxes and matrix transforms in JavaScript. The downsides of this approach are:
* Synchronization lag & visual tearing: Scrolling, zooming, or camera movements in 3D frequently could cause the overlay DOM elements to drift or jitter relative to the canvas pixels due to frame-timing differences.
* Clipping and z-ordering limitations: HTML overlays always sit on top of the entire canvas canvas buffer. Embedding HTML inside a 3D scene (e.g., behind a 3D object, inside a glass material, or reflected in a mirror) was impossible without complex iframe-to-image hacks.
* Performance overhead: To keep overlays aligned with the canvas, you have to recalculate each overlay's transform in JavaScript and write it to `style.transform` on every frame. The browser then parses each string and recalculates the element's style before it can render the frame, so main-thread work grows with every overlay that you add. In a 2D context, `drawElementImage()` updates the element's position for you. In WebGL and WebGPU, you pass the transform that you calculate to `updateElementGeometry()` as a matrix. Either way, the browser doesn't parse CSS or recalculate styles.


HTML-in-Canvas: Benefits
With the new HTML-in-Canvas API, you don't have to choose. By placing HTML inside the `<canvas>` element and synchronizing its transform, you ensure the content remains fully interactive, and that all browser integrations function automatically.


Here's what you get by letting the DOM handle your UI inside a `<canvas>` element:


* Text layout and formatting: Support for text layout and formatting, including multiline or bidirectional text with CSS styles applied.
* Form controls: Expressive form controls with extensive CSS and shader customization options.
* Text selection, copy/paste, and right-click: Users can highlight text inside 3D scenes or trigger context menus natively.
* Accessibility: HTML content rendered inside the canvas is exposed to the accessibility tree for screen readers.
* Browser features integration: Browser features like translate, autofill, or find-in-page work out of the box. Users can translate or search for text inside WebGL and WebGPU textures.
* Extension integration: Browser extensions work natively. For example, a text-replacement extension automatically updates the text rendered on your 3D meshes.
* DevTools integration: Inspect and tweak CSS styles for canvas UI elements directly in Chrome DevTools.
* Indexability and AI agents: Web crawlers and AI agents can index DOM content rendered into 2D and 3D scenes.
* Media editing and export: Export full canvas composites containing live DOM elements directly to images (`toDataURL()`, `toBlob()`) or video streams (`captureStream()`).

On the left, the canvas content is rendered using HTML-in-Canvas; the content is selectable and translatable, and browser features like autofill work out of the box. Use cases
This API unlocks potential across several domains:
* Large canvas-based applications: Heavyweight web apps can now render complex application UI components natively into their canvas-driven workspaces, improving accessibility and reducing bundle weight.
* 3D scenes and games: Marketing sites, immersive WebXR experiences, and web games can now place fully interactable web UI into 3D scenes—like a 3D book that uses real DOM text, or an in-game terminal that natively supports copying and pasting.
* Media editing and export. Creative tools like image generators, video editors, and design platforms often need to combine rich, styled HTML typography, templates, or user watermarks with direct pixel manipulation and shader effects. Because HTML-in-Canvas renders the DOM directly into the canvas pixel buffer, the entire composite can be exported directly as an image (such as with `toDataURL()` or `toBlob()`) or recorded into video frames with `captureStream()`. This improves rendering performance and visual fidelity compared to client-side libraries that attempt to reconstruct the DOM in JavaScript before export.
* Stunning UIs. Combining HTML and Canvas unlocks the capability to directly manipulate HTML content as pixels. This allows for a broader range of effects. With HTML-in-Canvas, you can re-imagine your UI to impress your users.

HTML-in-Canvas: Technical concepts
The HTML-in-Canvas API allows you to render interactive, accessible DOM subtrees directly into 2D, WebGL, or WebGPU canvas contexts. 


This guide outlines HTML-in-Canvas technical concepts that are common across all the canvas contexts:
* Prepare your canvas to render HTML
* Understand `drawable` subtree
* Understand the `paint` event
* Update element's geometry 
* Understand accessibility of HTML-in-Canvas 
* Use fallback strategies
Prepare your canvas to render HTML
To render HTML elements inside a `<canvas>`, you must configure two attributes:


* Set `content="drawable"` on the `<canvas>`: This opts the canvas element into laying out its descendant DOM nodes instead of treating them solely as hidden content.
* `drawable` on target elements: Marks an element as an independent paint root eligible for canvas rendering.




<canvas id="mainCanvas" width="600" height="400" content="drawable">
  <div id="parentElement" class="card" drawable>
    <h2>Container Title</h2>
    <p>Descriptive text inside the parent element.</p>
    <!-- Nested drawable: excluded from parentElement and drawn independently -->
    <button id="childElement" class="btn" drawable>Action Button</button>
  </div>
</canvas>


Understanding the drawable subtree 
When preparing your HTML to be rendered into a canvas, you need to decide which elements should be drawn independently. Each `drawable` element represents an independent paint root and its drawable subtree. 
A drawable subtree consists of an element with the `drawable` attribute and all of its descendants, excluding any nested descendants that also carry `drawable`, for example:


<canvas content="drawable">
  <!-- Subtree A (Renders parent container and text) -->
  <div id="parentElement" drawable>
    <h2>Parent Card Heading</h2>
    <p>Card body text content.</p>
    <!-- Subtree B (Excluded from Subtree A and drawn separately) --> 
    <button id="nestedChildElement" drawable>
      Clickable Button
    </button>
  </div>
</canvas>



Element
	Paint boundary
	Behavior
	`#parentElement` (Subtree A)
	Background panel, heading, and paragraph
	Rendered when calling `drawElementImage(parentElement, ...)`
	`#nestedChildElement` (Subtree B)
	Button surface and text
	Excluded from `#parentElement` subtree; rendered in a separate `drawElementImage(nestedChildElement, ...)` call
	Nesting drawable elements lets you maintain semantic HTML relationships while giving you the freedom to layer, position, or animate child elements independently over your canvas scene.


Understand the `paint` event
The HTML-in-Canvas API introduces the `paint` event. The browser automatically dispatches a `paint` event on the `<canvas>` whenever layout, text, or CSS styles change on any of its `drawable` descendants.


canvas.addEventListener("paint", (event) => {
  // Clear the viewport
  ctx.clearRect(0, 0, canvas.width, canvas.height);


  // Redraw elements individually
  ctx.drawElementImage(parentElement, 20, 20);
  ctx.drawElementImage(childElement, 40, 90);
});

The `paint` event dispatches an instance of `CanvasPaintEvent` which extends standard DOM Event and has a `changedElements` property that contains only the `drawable` descendants that visually changed (for example, style changes, layout shifts, text edits, focus state changes) since the last paint.


canvas.addEventListener("paint", (event) => {
  // Array of changed elements 
  for (const el of event.changedElements) {
    console.log(`Element #${el.id} visually changed and needs repainting`);
  }
});
Frame lifecycle
Canvas drawing commands executed inside the `paint` event appear in the current rendering update, but DOM modifications made inside the `paint` event do not show up until the subsequent frame:


canvas.addEventListener("paint", () => {
  // Renders in the CURRENT rendering update:
  ctx.drawElementImage(parentElement, 20, 20);


  // Modifying DOM styles inside paint schedules a new layout cycle;
  // changes will appear in the NEXT frame:
  parentElement.style.backgroundColor = "#e0f2fe";
});



Note: If a DOM change you make inside the `paint` handler changes how a `drawable` element renders, the browser fires another `paint` event on the next rendering update. To make style changes that take effect on the current rendering update, make these updates inside a `requestAnimationFrame` callback, which runs before the paint event for a given rendering update.
Nested canvases
If your page contains nested `<canvas content="drawable">` elements, the browser dispatches `paint` events in reverse DOM tree order (descendants fire before ancestors). This ensures child canvas elements render before parent canvas elements composite them.


Suppose in the following example the inner `nestedElement` element must visually change (say, its CSS background color changes on hover). First, the `paint` event fires on the `nestedCanvas` canvas. Its listener clears the child buffer and calls `ctx.drawElementImage(nestedElement, ...)` to render the updated hover state. Then the `paint` event fires on `parentCanvas`. Its listener draws `wrapperElement` (which contains the already-updated `nestedCanvas` canvas) into the scene.


<!-- Outer parent canvas -->
<canvas id="parentCanvas" width="800" height="600" content="drawable">
  <!-- Wrapper container for nested content -->
  <div id="wrapperElement" drawable>
    
    <!-- Nested child canvas -->
    <canvas id="nestedCanvas" width="300" height="200" content="drawable">
      <div id="nestedElement" class="badge" drawable>
        Inner Child Content
      </div>
    </canvas>
    
  </div>
</canvas>


<script>
const parentCanvas = document.getElementById("parentCanvas");
const parentCtx = parentCanvas.getContext("2d");


const nestedCanvas = document.getElementById("nestedCanvas");
const nestedCtx = nestedCanvas.getContext("2d");


const nestedElement = document.getElementById("nestedElement");
const wrapperElement = document.getElementById("wrapperElement");


// ============================================================================
// 1. Child Canvas Listener (Fires FIRST)
// ============================================================================
nestedCanvas.addEventListener("paint", (event) => {
  // Clear and redraw the child canvas with the updated inner element
  nestedCtx.clearRect(0, 0, nestedCanvas.width, nestedCanvas.height);
  nestedCtx.drawElementImage(nestedElement, 10, 10);
  
  console.log("1. Child nested canvas rendered fresh pixels.");
});


// ============================================================================
// 2. Parent Canvas Listener (Fires SECOND)
// ============================================================================
parentCanvas.addEventListener("paint", (event) => {
  // Clear and redraw the parent canvas scene
  parentCtx.clearRect(0, 0, parentCanvas.width, parentCanvas.height);
  
  // Draws the wrapper container (including the freshly painted nestedCanvas)
  parentCtx.drawElementImage(wrapperElement, 50, 50);
  
  console.log("2. Parent canvas composited the complete scene.");
});
</script>

Trigger paint event
You can call `requestPaint()` to schedule a single `paint` event on the next frame, even if no DOM text or styles have changed. This can be used for rendering interactive scenes with moving elements, for example:


let animatedX = 0;


function animationLoop() {
  animatedX += 1.5; // Move the element horizontally
  
  // Request canvas paint for smooth animation
  canvas.requestPaint();
  
  requestAnimationFrame(animationLoop);
}


canvas.addEventListener("paint", () => {
  ctx.clearRect(0, 0, canvas.width, canvas.height);

Update element's geometry
After rendering the element image into your canvas, you may need to synchronize the DOM and the pixels[i][j]. In 2D context, the browser handles geometry synchronization automatically by default, while in 3D you need to create a transform and pass it to the `updateElementGeometry()` method.


To update the geometry, pass a spatial transform to the method.  Learn more how to construct a transform for different contexts:
* Synchronize geometry in 2D.
* Synchronize geometry in WebGL.

Manage hit-test stacking order
By default, every time an element’s geometry is updated, the browser brings it to the top of the interaction stack (last drawn = topmost click target). You can control this behavior using `preserveHitTestOrder`:


// Updates the backdrop without stealing clicks from foreground elements
canvas.updateElementGeometry(backgroundElement, {
  canvasTransform: customTransform,
  preserveHitTestOrder: true
});



Option
	Behavior
	Use case
	`preserveHitTestOrder: false` (default)
	Moves the element to the top of the hit-test stack.
	Foreground elements that should receive clicks first.
	`preserveHitTestOrder: true`
	Leaves the element at its current stack priority.
	Background elements that need to be updated after the foreground elements.
	

Reset geometry
To un-draw an element without removing it from the DOM, call `canvas.clearElementGeometry()`. This resets the element's canvas transform and marks it as offscreen in the accessibility tree:


// Remove from canvas hit-testing and mark as offscreen 
canvas.clearElementGeometry(childElement);

Sizing and units
When you draw HTML into a canvas, the browser operates in three coordinate systems at once:  CSS pixels, device pixels, and canvas grid pixels. 


CSS pixels are used for measuring and positioning content during layout. The browser then scales them by devicePixelRatio to rasterize the page into physical device pixels. Because CSS pixels are a logical unit, positions and sizes often end up as fractions of a device pixel (for example, 10.5 CSS px × a DPR of 1.5 = 15.75 device px). A screen can only colour whole pixels, so the browser has to resolve anything that falls between them. It does this in two ways:


* Snapping: box boundaries, borders and layer offsets are rounded to the nearest whole device pixel so they stay crisp
* Anti-aliasing: for text glyphs, curves and transformed edges, partial coverage is blended into neighbouring pixels so they still look smooth and in the right place.


A `<canvas>` has its own pixel grid, set by its `width` and `height` attributes, which is separate from both CSS pixels and device pixels. To display it, the browser resamples the canvas bitmap onto the physical pixel grid, blending neighbouring canvas pixels to fill each device pixel. To learn how the browser maps between CSS, canvas, and device pixels, see Pixel-perfect rendering with `devicePixelContentBox`.


Your `drawable` HTML elements are laid out in CSS pixels. Because content drawn into a canvas can go through two conversions, from CSS pixels to the canvas grid and then from the canvas grid to physical pixels, each step that doesn't line up exactly adds another round of blending, and the result can look blurry. To avoid this, make the canvas grid match the physical pixel grid. This serves two purposes:
* Consistent rendering: If the canvas maps 1:1 onto physical pixels, converting CSS pixels to canvas pixels produces the same result as the browser's conversion from CSS pixels to physical pixels for regular HTML.
* No extra blending: If the canvas maps 1:1 onto physical pixels, converting it to device pixels doesn't add any blur.












  

Example of a pixel conversion that results in blurry content. The three grids don't line up: The canvas element is 360 × 180 CSS px, and the canvas size is 300 × 150 canvas grid pixels. At a device pixel ratio of 1.5, the canvas covers 540 × 270 device pixels. One CSS pixel spans 1.5 device pixels, and one canvas pixel spans 1.2 CSS px, or 1.8 device pixels (panel 1). When the circle is drawn, its position and radius are in canvas pixels, not CSS pixels, so the browser draws it into the 300 × 150 canvas bitmap and anti-aliases the edge (panel 2). To display the canvas, the browser then stretches this bitmap over 540 × 270 device pixels, so the browser has to interpolate: each device pixel takes a weighted mix of the nearest canvas pixels, which already contain the anti-aliased edge. The edge is blended a second time and spreads across several device pixels, so the circle looks blurry (panel 3). This could be avoided if the canvas grid matched the device pixels 1:1. The browser would then anti-alias the edge just once, directly on the device grid, and display the bitmap without resampling, so the edge stays crisp (panel 4).[k]




For crisp rendering, the canvas grid must match the number of device pixels that the canvas covers: 540 × 270 in the example above.
  

The same canvas, 400 x 200 CSS pixels, on a screen with a DPR of 1.5. Left: the 400 x 200 canvas grid. Right: adjusted to the DPR, a 600 x 300 grid.


Size the canvas grid with a resize observer
The right grid size depends on the device, and it may change when the layout changes, when the user zooms the page, or when the user moves the window to a different display. So instead of hardcoding the grid size, let the browser tell you what it should be.


To keep the canvas grid in sync with the canvas on screen, always size it with a `ResizeObserver` and adjust the canvas grid to `devicePixelContentBoxSize`:


const observer = new ResizeObserver(([entry]) => {
  const dpc = entry.devicePixelContentBoxSize;
  canvas.width = dpc ? dpc[0].inlineSize : Math.round(entry.contentRect.width * window.devicePixelRatio);
  canvas.height = dpc ? dpc[0].blockSize : Math.round(entry.contentRect.height * window.devicePixelRatio);
});


const supportsDevicePixelContentBox =
  typeof ResizeObserverEntry !== 'undefined' &&
  'devicePixelContentBoxSize' in ResizeObserverEntry.prototype;
const options = supportsDevicePixelContentBox ? { box: 'device-pixel-content-box' } : {};
observer.observe(canvas, options);

Note: Setting `width` or `height` clears the canvas, even if the value doesn't change. In a 2D context, it also resets the context state. When your resize observer updates the grid because the canvas was resized, the `paint` event fires afterward in the same frame. If you change the grid size anywhere else, call `canvas.requestPaint()` to make sure that the paint event fires and you can redraw.
Convert CSS pixels to canvas grid coordinates
In your `paint` handler, you often combine DOM measurements with drawing calls—for example, to position an element based on its size. The two use different units:


* Canvas pixels describe the canvas grid, which is sized by `canvas.width` and `canvas.height`. For example, the `dx`, `dy`, `dwidth`, and `dheight` parameters of the `drawElementImage()` drawing methods, or other canvas APIs parameters, such as `fillRect()` and `translate()`.
* CSS pixels describe the page. DOM measurements such as `offsetWidth` and `clientWidth`, and pointer event coordinates such as `offsetX`, are in CSS pixels.


Here's an overview of the units used by various API parameters:


Value
	Units
	`canvas.width` and `canvas.height`
	Canvas grid pixels
	2D drawing parameters, including `dx`, `dy`, `dwidth`, and `dheight` of `drawElementImage()`
	Canvas grid pixels
	`width` and `height` returned by `canvas.ElementImageDefaultSize()`
	Canvas grid pixels
	Source rectangles: `sx`, `sy`, `swidth`, and `sheight` of `drawElementImage()` and `texElementSubImage2D()`; `sourceX`, `sourceY`, `sourceWidth`, and `sourceHeight` of `drawElementImageToTexture()`
	CSS pixels
	Texture sizes: `width` and `height` options of `texElementSubImage2D()`; `size` of `drawElementImageToTexture()`
	Texture pixels. By default, the element's size in canvas grid pixels, rounded up
	Element geometry: `getElementTransform()`, and the `canvasTransform` and `canvasClip` options of `updateElementGeometry()`
	CSS pixels
	DOM measurements, such as `offsetWidth`, `clientWidth`, `getBoundingClientRect()`, pointer event coordinates, and `contentBoxSize` of a resize observer entry
	CSS pixels
	`devicePixelContentBoxSize` of a resize observer entry
	Device pixels
	

If you don't use the right units, the size of the HTML content drawn into canvas might not meet your expectations. You need to convert the CSS pixel value into canvas grid pixels when drawing HTML into canvas. To do so, calculate the ratio between the canvas grid size and the canvas CSS size: `canvas.width / cssContentWidth` horizontally, and `canvas.height / cssContentHeight` vertically. Your resize observer is a convenient place to calculate the ratio as follows:


// The number of canvas grid pixels per CSS pixel  
let scaleX = 1;
let scaleY = 1;


const observer = new ResizeObserver(([entry]) => {
  const dpc = entry.devicePixelContentBoxSize;
  const cssContentWidth = entry.contentRect.width;
  const cssContentHeight = entry.contentRect.height;

 // Best practice: make the canvas grid match the physical pixel grid
  if (dpc) {
    canvas.width = dpc[0].inlineSize;
    canvas.height = dpc[0].blockSize;
  } else {
    canvas.width = Math.round(cssContentWidth * window.devicePixelRatio);
    canvas.height = Math.round(cssContentHeight * window.devicePixelRatio);
  }


  scaleX = canvas.width / cssContentWidth;
  scaleY = canvas.height / cssContentHeight;
});


const supportsDevicePixelContentBox =
  typeof ResizeObserverEntry !== 'undefined' &&
  'devicePixelContentBoxSize' in ResizeObserverEntry.prototype;
const options = supportsDevicePixelContentBox ? { box: 'device-pixel-content-box' } : {};
observer.observe(canvas, options);

Then, multiply CSS pixel values by `scaleX` and `scaleY` before you pass them to the drawing method. For example, to center a drawable element in the canvas:


const ctx = canvas.getContext('2d');
const card = document.getElementById('card');


canvas.onpaint = () => {
  ctx.reset();


  // offsetWidth and offsetHeight are in CSS pixels.
  // Convert them to canvas grid coordinates.
  const width = card.offsetWidth * scaleX;
  const height = card.offsetHeight * scaleY;
  const x = (canvas.width - width) / 2;
  const y = (canvas.height - height) / 2;


  // drawElementImage() takes canvas grid coordinates.
  ctx.drawElementImage(card, x, y);
};

Understand accessibility of HTML-in-Canvas
Generally, HTML content of a `<canvas content="drawable">` is exposed to accessibility in the same way as regular DOM, which means it is represented in the accessibility tree unless explicitly hidden using attributes like `aria-hidden="true"` or inert. However, there is one key exception: a `drawable` element whose rendered geometry has not yet been established or updated. 


A `drawable` element inside a `<canvas content="drawable">` lacks rendered geometry if:
* It has not yet been rendered with `drawElementImage()` which updates geometry automatically by default.
* Its geometry has not been explicitly updated with `updateElementGeometry()`. 


If a `drawable` element lacks rendered geometry, this `drawable` element and its `drawable` subtree are reported to the accessibility tree without geometry information. This is helpful, for example, to let screen readers access the semantic content, while signaling visual assistive tools (like magnifiers) to filter out the undrawn elements.

Synchronize the DOM and the pixels
Because `<canvas>` rendering is imperative while DOM layout and CSS styling are reactive, the browser needs a mechanism to keep the rendered canvas pixels, interactive hit-test regions, and accessibility trees synchronized. Before diving into how to synchronize the DOM and the pixels, make sure you understand the `paint` event that triggers when DOM elements update and need to be redrawn.


In 2D canvas contexts, the browser automatically synchronizes the element's layout coordinates, accessibility bounds, and pointer hit-testing with the drawn canvas coordinates.
Manually update element geometry
In advanced scenarios, you can opt out of automatic geometry synchronization and control spatial transforms manually. Pass `{ preserveElementGeometry: true }` to `drawElementImage()` to prevent the browser from automatically overriding the element's existing hit-test coordinates:


// 1. Draw the element without altering its existing hit-test bounds
ctx.drawElementImage(targetElement, elementX, 200, { preserveElementGeometry: true });


// 2. Construct a custom transform matrix as needed,
// assuming scaleX/scaleY = canvas grid pixels per CSS pixel, 
// from your resize observer (see "Units and sizing"). 
 const currentTransform = new DOMMatrix();
 currentTransform.a = 1.5;    // scale X
 currentTransform.e = x / scaleX; // translate X: grid px → CSS px
 currentTransform.f = y / scaleY; // translate Y: grid px → CSS px


// 3. Explicitly apply the custom transform
canvas.updateElementGeometry(targetElement, { canvasTransform: currentTransform });

HTML in WebGL canvas
Rendering HTML inside a WebGL canvas allows you to use live DOM subtrees as dynamic GPU textures. Rendering HTML into a WebGL canvas allows you to apply shader effects on Live DOM or integrate interactive HTML into 3D scenes. 


This guide demonstrates how to render HTML into a WebGL canvas. Learn more about HTML-in-Canvas in the API overview.[m]


Rendering a HTML-in-Canvas in a WebGL context requires the following steps:
1. Prepare your canvas. Declaratively set the right attributes to let the browser know it should render HTML into a canvas. This setup is identical across 2D, WebGL, and WebGPU contexts. Learn how to set your canvas up and how to declare HTML elements to be drawn independently.  
2. Apply the HTML as a texture:
   1. Pre-allocate GPU texture storage
   2. Upload the DOM snapshot as texture
3. Synchronize the DOM and the pixels.
Draw HTML element as WebGL texture
In WebGL, HTML elements are uploaded to the GPU as 2D textures using texElementSubImage2D(). 
Pre-allocating texture storage
Unlike 2D canvas which manages backing memory automatically, WebGL context requires explicit memory management. 
Before uploading DOM pixels, you must pre-allocate GPU memory. This allows the browser to perform fast sub-image updates without triggering expensive GPU memory re-allocations.


Pre-allocate buffer with the desired size parameters and the `srcData` set to `null`  as follows: 


// Only allocate texture backing once
if (!textureBufferAllocated) {
// Pre-allocate texture backing with pre-determined size.
gl.texImage2D(
/* target */ gl.TEXTURE_2D,
/* level */ 0,
/* internalformat */ gl.RGBA8,
/* width */ myElementWidth,
/* height */ myElementHeight,
/* border */ 0,
/* format */ gl.RGBA,
/* type */ gl.UNSIGNED_BYTE,
/* srcData */ null
);


textureBufferAllocated = true;
}

For the texture to match the natural layout size of the HTML element, you can use `canvas.getElementImageDefaultSize()` to retrieve its default size in canvas grid pixels:



const { width, height } = canvas.getElementImageDefaultSize(myElement);
// Pre-allocate texture backing. Only do this once, or whenever the element
// changes size.
gl.texImage2D(
   /* target */ gl.TEXTURE_2D,
   /* level */ 0,
   /* internalformat */ gl.RGBA8,
   /* width */ Math.ceil(width),
   /* height */ Math.ceil(height),
   /* border */ 0,
   /* format */ gl.RGBA,
   /* type */ gl.UNSIGNED_BYTE,
   /* srcData */ null);
Upload the DOM snapshot as texture
The next step is to upload the HTML element into your texture inside your render loop or `paint` listener. 
canvas.onpaint = () => {
// 1. Pre-allocate texture backing first
// ...


// 2. Upload HTML snapshot into the WebGL texture
gl.texElementSubImage2D(
  /* target  */ gl.TEXTURE_2D,
  /* level   */ 0,
  /* xoffset */ 0,
  /* yoffset */ 0,
  /* element */ myElement // or an ElementImage from `captureElementImage()`
);


// ... 
};
Synchronize geometry
Unlike in 2D contexts, the browser cannot automatically infer where the texture appears on screen in 3D context. You need to align DOM hit-testing and accessibility bounding boxes with your 3D mesh manually.
To do so, construct a `DOMMatrix` that maps the element’s border box to its rendered canvas pixel location, then apply it using `updateElementGeometry()`:


canvas.addEventListener("paint", () => {
  // 1. Upload fresh DOM snapshot to GPU texture
  gl.bindTexture(gl.TEXTURE_2D, myTexture);
  gl.texElementSubImage2D(gl.TEXTURE_2D, 0, 0, 0, myElement);


  // 2. Draw your 3D scene
  draw3DScene();


  // 3. Construct the CSS-pixel transform mapping the element's
  // border box to its drawn position on the canvas as needed
  // (for example: scale and translate) 
  const canvasTransform = new DOMMatrix();
  // scale X
  canvasTransform.a = canvas.clientWidth / myElement.offsetWidth;
  // scale Y 
  canvasTransform.d = canvas.clientHeight / myElement.offsetHeight;  
  // translate X (CSS px) 
  canvasTransform.e = 50;
  // translate Y (CSS px)                                          
  canvasTransform.f = 100;                                          


  // 4. Update DOM position, accessibility focus rings, and pointer hit-testing
  canvas.updateElementGeometry(myElement, {
    canvasTransform: canvasTransform,
  });
});

HTML in WebGPU Canvas
Rendering HTML inside a WebGPU canvas offers all the benefits that HTML in a WebGL canvas does, such as applying shader effects on DOM or integrating interactive HTML into 3D scenes. However, WebGPU offers significant benefits compared to WebGL. 


This guide demonstrates how to render HTML into a WebGPU canvas. Learn more about HTML-in-Canvas in the API overview[n].


Rendering a HTML-in-Canvas in a WebGPU context requires the following steps:
1. Prepare your canvas. Declaratively set the right attributes to let the browser know it should render HTML into a canvas. This setup is identical across 2D, WebGL, and WebGPU contexts. Learn how to set your canvas up and how to declare HTML elements to be drawn independently.

   1. Pre-allocate GPU texture storage
   2. Upload the DOM snapshot as texture

Draw HTML element as WebGPU texture
In WebGPU, HTML elements are uploaded to the GPU as 2D textures using `drawElementImageToTexture()`. 
Pre-allocating texture storage
WebGPU requires explicit memory allocation. Before copying DOM pixels into a texture, you must reserve GPU VRAM using the device.createTexture() method:


const context = canvas.getContext("webgpu");


// Pre-allocate the texture size as needed
// For example: HTML element CSS size × devicePixelRatio 
const size = canvas.getElementImageDefaultSize(myElement);
const myElementWidth = Math.ceil(size.width);
const myElementHeight = Math.ceil(size.height);


// Pre-allocate the GPUTexture backing (run once during setup)
const myTexture = device.createTexture({
  size: {
    width: myElementWidth,
    height: myElementHeight,
    depthOrArrayLayers: 1, // optional (defaults to 1)
  },
  format: "rgba8unorm",
  usage:
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.COPY_DST |
    GPUTextureUsage.RENDER_ATTACHMENT,
});

HTML in Offscreen Canvas[o]
An `OffscreenCanvas` provides a canvas rendering context that can be transferred and executed entirely inside a dedicated Web Worker thread, decoupled from the browser's main thread.
In high-performance web applications, compute-intensive rendering loops, particle simulations, or continuous 3D rasterization can consume significant CPU and GPU cycles.
When these operations run on the main thread, they compete with user clicks, smooth scrolling, and CSS animations. Moving canvas rendering to an `OffscreenCanvas` in a Web Worker ensures that even if the worker's rendering pipeline slows down or temporarily stalls, the main browser thread remains completely responsive and stutter-free.
Offload rendering to a worker thread
Because Web Workers do not have access to the document or live DOM elements, offloading HTML-in-Canvas rendering involves transferring canvas ownership and passing element snapshots between threads.
Main thread setup
To offload the canvas to the worker thread, set up your main thread as follows:
1. Create the worker.
2. Transfer canvas control to an OffscreenCanvas instance using `transferControlToOffscreen()`.
3. Listen for the `paint` event on the `<canvas content="drawable">`. Inside the listener, capture a snapshot of the DOM element using `captureElementImage(element)`, then post it to the worker:
// main thread


// 1. Instantiate the Web Worker
const worker = new Worker("/path/to/worker");


// 2. Transfer canvas control to the worker
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ type: "INIT", canvas: offscreen }, [offscreen]);


// 3. Capture and forward element snapshots on paint
canvas.addEventListener("paint", () => {
  const elementImage = canvas.captureElementImage(htmlElement);
  // Post the ElementImage snapshot to the worker
  worker.postMessage({ type: "DRAW", image: elementImage });
});
Worker thread setup
In the worker, listen for messages to receive the offscreen canvas and draw the incoming `ElementImage` snapshots:
// worker thread 
self.onmessage = (event) => {
  const { type, canvas, image } = event.data;


  if (type === "INIT") {
    // Obtain 2D, WebGL, or WebGPU context on the worker thread
    ctx = canvas.getContext("2d");
  } else if (type === "DRAW" && ctx) {
    // Clear and draw the ElementImage snapshot
    ctx.clearRect(0, 0, ctx.canvas.width, ctx.canvas.height);
    ctx.drawElementImage(image, 20, 20);
  }
};

Synchronize geometry from a Worker
Web Workers do not have access to DOM APIs (for example, `document.getElementById`, `element.style`, or DOM node references). Because of this sandbox boundary, the worker thread posts a task to the main thread, and the update happens on the main thread. When the update is complete, the main thread fires an `elementgeometryupdate` event on the associated `HTMLCanvasElement`.
When a worker calls `updateElementGeometry()` or `clearElementGeometry()` it then asynchronously posts[p] the batched updates to the main thread:
// worker thread 
const canvasTransform = new DOMMatrix().translateSelf(50, 100);


// Pass the ElementImage reference and custom transform from the worker
offscreenCanvas.updateElementGeometry(elementImage, {
  canvasTransform: canvasTransform
});

The main thread applies the changes to the underlying DOM elements. Once the main thread finishes updating the DOM interaction bounding boxes, it dispatches an `elementgeometryupdate` event on the associated `<canvas>` element containing the list of updated elements:
// main thread
// Listen for confirmation of applied geometry changes 
canvas.addEventListener("elementgeometryupdate", (event) => {
  console.log("DOM hit-test geometry successfully updated from worker:", event);
});
